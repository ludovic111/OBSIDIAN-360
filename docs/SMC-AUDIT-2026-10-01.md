## Défaut du cache

`smc_reply` possède treize entrées de seize octets, avec les identifiants `01 04 07 0a 0f 11 12 13 16 17 1e 20 83`. Aucune entrée sentinelle nulle ne termine le tableau. La recherche originale attend pourtant cette sentinelle : pour un identifiant absent, elle lit au-delà des 208 octets alloués.

Le banc `research/tests/check-smc-cache.py` extrait le tableau et la fonction C réels puis les compile avec AddressSanitizer. Les treize identifiants connus passent. Le parcours des 256 valeurs possibles provoque un `global-buffer-overflow` dans l'original ; avec le correctif borné par `ARRAY_SIZE`, il termine avec exactement treize correspondances. Les quatre cas vérifient leur résultat attendu. Preuve : `smc-audit/cache-bounds.json`.

Le candidat `0004-xenon-bound-smc-reply-cache.patch` borne uniquement cette recherche. Il ne corrige pas les autres limites du protocole et ne prouve pas la cause du gel NAND E10. Le défaut de source et sa présence dans le code installé sont confirmés ; son déclenchement sur la console n'a pas été testé.

## Transport et concurrence : analyse du code

| Partie | Comportement constaté dans les sources | Limite |
|---|---|---|
| Envoi | Message de 16 octets, quatre mots dans le FIFO à l'offset `0x80`, contrôle `0x84` | Boucle d'attente de disponibilité sans délai maximal, sous verrou avec interruptions locales désactivées |
| Réception | FIFO `0x90`, contrôle `0x94`, réponse recopiée dans le cache | Cache partagé global ; pas d'identifiant de transaction |
| Attente | Les messages avec bit `0x80` ne sont pas attendus ; les autres attendent `smc.cmd == msg[0]` | Aucun délai maximal ; retour de `wait_event_interruptible` ignoré |
| Synchronisation | Verrou autour de chaque transfert FIFO | Pas de mutex couvrant toute la séquence envoi/attente/lecture |
| Interruption | Statut `0x50`, acquittement `0x58`, mise à jour du cache et réveil | Le gestionnaire renvoie `IRQ_NONE` même après réception ; impact à analyser |
| Interface utilisateur | `/dev/smc` exige un message de 16 octets et limite l'ouverture à un seul utilisateur | Cette restriction ne sérialise pas les consommateurs internes ANA, horloge et températures |

Des réponses anciennes ou entrelacées sont des risques déduits de ces chemins, pas des incidents reproduits. Aucun test de concurrence avec le SMC physique n'a été effectué. La lecture ANA ne valide pas explicitement un statut de réponse avant de décoder les octets de données ; cela limite la portée des captures antérieures.
